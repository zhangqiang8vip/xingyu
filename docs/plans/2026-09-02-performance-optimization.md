## 0. 2026-09-02 线上基线审计结论

本节是 Codex 在未修改业务代码的前提下，对当前生产版本完成的首轮实测。Core Web Vitals 的目标采用 [web.dev 官方定义](https://web.dev/articles/vitals)：LCP `≤ 2.5s`、INP `≤ 200ms`、CLS `≤ 0.1`；性能录制与瓶颈归因依据 [Chrome DevTools Performance 官方说明](https://developer.chrome.com/docs/devtools/performance)。本次数据是实验室基线，不代替后续真实用户监控（RUM）。

### 0.1 测试条件与结果

| 页面 | 条件 | TTFB | LCP | CLS | 请求/传输 | 结论 |
| --- | --- | ---: | ---: | ---: | --- | --- |
| `/` | 桌面 1440×900、无节流、缓存命中 | 757ms | 1,017ms | 0 | 34 个请求 | 桌面边缘命中良好 |
| `/` | 移动 390×844、4× CPU、Slow 4G、冷缓存 | 214ms | 3,463ms | 0 | 35 个请求、约 496KB | 需要改进；93.8% LCP 时间是响应后的渲染延迟 |
| `/archive` | 移动 390×844、4× CPU、Slow 4G、冷缓存 | 198ms | 3,305ms | 0 | 同样受全局 CSS 关键链影响 | 不是首页单点问题 |
| 普通文章 | 桌面、无节流、冷缓存 | 205ms | 752ms | 0 | 未单列 | 桌面基础路径良好 |
| 富内容文章 | 移动 390×844、4× CPU、Slow 4G、冷缓存 | 208ms | 3,993ms | 0 | 74 个请求、约 871KB | 接近 LCP “较差”边界；CSS、KaTeX 字体和图片共同阻塞 |
| `/admin/login` | 桌面、无节流 | 750ms | 1,050ms | 0 | CSS 额外包含 Vditor 样式 | 登录页不应携带编辑器样式 |

未记录的 FCP/INP 不作推测。INP 需要真实交互样本或专门的交互录制，不能用 LCP 代替。

从当前 Windows 网络直接请求生产域名的补充观测：公开首页三次 TTFB 分别约为 `5.09s / 3.36s / 2.82s`，归档页约为 `2.23s / 1.45s / 1.48s`；同一首页的缓存命中响应里，`Server-Timing` 只报告约 `11ms` 边缘处理和 `6ms` Worker 处理，且 `cf-ray` 落到 `PDX`。因此国内体感慢不能简单归因成 Worker 执行慢，跨境路由和边缘节点位置是独立变量。Cloudflare 官方也说明，流量经中国大陆以外节点会面临显著延迟和可靠性问题；其 [China Network](https://developers.cloudflare.com/china-network/) 需要 Enterprise 独立订阅并要求域名具备 ICP 备案/许可证。本项目当前阶段应先完成前端瘦身与分层计时，再决定是否值得改变部署架构。

### 0.2 已确认的主要瓶颈

#### P0：公开页面首屏被全局 CSS 和隐藏的富文本依赖拖慢

- `site/app/globals.css` 源文件约 `343KB`；生产压缩后仍约 `73KB`，在移动冷缓存中是渲染阻塞资源，单次关键链约 `2.74–3.16s`。
- `site/app/layout.tsx:3` 全局导入 KaTeX CSS，使不含公式的首页、归档和登录路径也承担公式样式成本。
- 首页静态依赖链为 `BlogHomeExperience → ModalPostLink → MarkdownRenderer`。后者静态导入 React Markdown、GFM、Raw HTML、Sanitize、Highlight、KaTeX 和 Mermaid 包装层。
- 移动首页初始 JavaScript 约 `370KB` 压缩、`1.17MB` 解压；其中 `MarkdownRenderer` chunk 单独约 `161KB` 压缩、`525KB` 解压，KaTeX JS 约 `80KB` 压缩。用户没有打开文章弹窗时也付出了这部分成本。

实施要求：先拆开“可点击文章卡片”和“真正打开后的阅读器”。阅读器及 Markdown 渲染器应在用户打开弹窗时加载；KaTeX、代码高亮和 Mermaid 继续按正文能力加载。验收以冷缓存 Network 为准：首页和归档初始请求不再包含这些富文本大包，同时弹窗、独立阅读和管理端阅读行为不变。

#### P0：首页数据载荷读取并传输了不需要的正文

- `site/db/queries.ts:65` 的 `listHomePosts()` 为所有首页卡片选择 `posts.content`。
- `site/features/home/BlogHomeExperience.tsx:89` 只在第一张精选卡片用正文估算阅读分钟，其余卡片不使用正文；点击阅读后本来就会通过 reader API 再取正文。

实施要求：卡片查询只返回真实需要的列。阅读时长可由数据库 `length(content)`、稳定的派生字段或保存时计算值提供，但不得为了一个展示值把全部正文注入首页 HTML/RSC。修改前后需要记录首页 HTML、RSC 和 D1 返回体积。

#### P1：富内容文章的字体和图片没有按展示尺寸交付

- KaTeX 两个字体使用阻塞式 font display，实测分别浪费约 `1,105ms` 和 `955ms`；Chrome 估算改为合适的 `swap/optional` 可改善首屏文字展示。
- 富内容文章的 `1823×863` 图片在移动端仅显示约 `360×170`，潜在节省约 `154.6KB`。
- `512×512` 头像在文章元信息中只显示约 `28×28`，潜在节省约 `20.5KB`；首页较大头像也可按实际尺寸提供响应式资源。

实施要求：优先复用现有 `/_vinext/image` 管线或框架图片能力，明确 `width/height/srcset/sizes`；不得牺牲清晰度或引入 CLS。KaTeX 字体策略必须回归公式渲染和明暗主题。

#### P1：登录页加载了编辑器 CSS，管理端动态耗时尚未分层

- `site/app/admin/layout.tsx:5` 对所有 `/admin` 路由注入 `/vditor/dist/index.css`，所以未登录的登录页也下载约 `9.4KB` 压缩、`43.5KB` 解压的编辑器样式。
- 登录页约 `750ms` TTFB，但当前没有证据能区分认证、设置查询、D1 或 Worker 启动成本。

实施要求：Vditor CSS 下沉到真正使用编辑器的路由或组件；同时为管理端请求增加不含敏感数据的 Server-Timing 分段。登录、草稿和私密内容继续 `no-store`，不以缓存掩盖动态耗时。

#### P1：公开缓存声明与实际 Cloudflare 语义不一致

- `site/worker/index.ts:34` 返回 `public, max-age=0, s-maxage=120, stale-while-revalidate=300`，并在 `caches.default` 中手动 `match/put`。
- Cloudflare 当前 [Workers Cache 配置文档](https://developers.cloudflare.com/workers/cache/configuration/) 明确指出，`s-maxage` 会禁用 `stale-while-revalidate`；其 [Cache API 文档](https://developers.cloudflare.com/workers/runtime-apis/cache/) 也说明 `cache.put/cache.match` 不支持 `stale-while-revalidate` 指令。

实施要求：先写清浏览器 TTL、边缘 TTL、后台刷新和发布失效的真实目标，再选用一种一致的机制。不得扩大当前公开文档白名单，也不得缓存 `/admin`、API、RSC、OAuth、MCP、私密预览或带身份的响应。

#### P1：生产页面存在 hydration mismatch

- Lighthouse/控制台捕获到 React minified error `#418`（text hydration mismatch）。这既是正确性问题，也可能触发客户端重建并增加渲染成本。
- 当前只能确认现象，不能确认根因；缓存 HTML 与新 RSC、动态浏览量、时间/区域格式化或服务端与客户端分支都属于待验证假设。

实施要求：先在开发构建复现并取得完整 React 报错组件栈，再做最小修复。禁止仅添加 `suppressHydrationWarning` 隐藏错误。

#### P2：低价值预取、构建重复资产和对比度

- `StableLink` 没有关闭框架预取；首页在 LCP 后预取 `/`、`/archive`、`/connect`、`/about` 的 RSC。它不是当前 LCP 主因，但会浪费移动数据和网络竞争。
- 文章页会预取上一篇/下一篇 HTML/RSC；需要按使用概率和阅读模式决定是否保留。
- `site/dist/client/vditor/js` 与 `site/dist/client/vditor/dist/js` 存在大量同名同尺寸文件，例如 Lute、Mermaid、Graphviz、MathJax 和 Highlight。这首先是部署/存储重复，不应误报成所有文件都进入公开首屏；需确认 Vditor 的实际 CDN 路径后去重。
- Lighthouse 得分：Accessibility `96`、Best Practices `96`、SEO `100`。浅色主题的分类、摘要、日期等若干文字对比度低于 WCAG AA（最接近的一处 `4.46:1`，其他约 `2.8–4.41:1`）。应在不破坏现有审美的前提下统一调整语义色 token。

### 0.3 暂未证实，不允许直接修改的方向

- `ensureDatabase()` 是否造成每个请求的 DDL/种子开销：源码存在模块级 Promise 和版本标记，必须先用分段计时确认。
- D1 查询或 Worker 冷启动是否是国内访问的主要慢点：目前网络路径证据更强，但尚无足够分层数据。
- 是否需要购买 Cloudflare China Network、迁移区域或引入新 CDN：属于成本、备案和架构决策，不是本轮可直接推导出的代码修改。
- 大型构建资产是否等于首屏下载：不能只看 `dist` 文件大小，必须以每条路由的网络瀑布为准。

### 0.4 建议拆分的实施批次

1. **PR 1：公开阅读器懒加载。** 切断首页/归档到 `MarkdownRenderer` 的静态依赖；保存同条件前后 trace 和初始 JS 请求清单。
2. **PR 2：CSS 路由化。** 从全局 CSS 中拆出仅文章、Markdown、KaTeX、管理端和编辑器需要的样式；用桌面/移动截图回归明暗主题。
3. **PR 3：首页载荷与预取。** 卡片查询移除正文，调整低价值 RSC 预取；对比 HTML/RSC/D1 体积。
4. **PR 4：字体与响应式图片。** 处理 KaTeX font-display、正文图片和头像尺寸；对比富内容文章 LCP、CLS 与清晰度。
5. **PR 5：管理端分层计时。** 编辑器 CSS 下沉、增加 Server-Timing、测量认证/设置/D1，再决定是否优化查询。
6. **PR 6：缓存契约修正。** 统一 Cache API 与响应头语义，并验证发布/撤回后的失效、HIT/MISS/过期、安全白名单。
7. **PR 7：正确性与可访问性。** 定位 hydration mismatch，微调浅色语义色 token；不得用屏蔽错误或大改设计交差。

每个批次独立复测和提交，不能把前端拆包、数据库、缓存与视觉 token 混成一个无法归因的大提交。

## 1. 为什么先做这项工作

当前第一阶段功能已形成完整 Demo，首轮线上基线已经确认公开移动端存在可复现的加载瓶颈，但还没有持续预算与真实用户数据。第 0 节结论用于决定实施顺序；后续仍须坚持“测量—定位—最小修改—复测”，禁止只凭构建体积或主观感受批量删依赖、改缓存或重写数据层。

## 4. 目标与质量门槛

### 4.1 用户体验目标

公开页面以 Core Web Vitals 的“良好”范围作为方向性目标：

- LCP：`≤ 2.5s`
- INP：`≤ 200ms`
- CLS：`≤ 0.1`

这是目标，不是允许伪造或通过隐藏内容达成的测试指标。若受当前运行架构、地域或第三方资源影响无法达到，实施者必须提交瓶颈证据和下一步建议。

### 4.2 项目验收门槛

1. 上述所有核心场景功能回归通过。
2. 首页和不含图表的文章不得在首屏下载 Vditor、Graphviz、MathJax 或 Mermaid 的大型运行时；以网络瀑布图为准。
3. 后台/私密响应不得因为性能优化变成公共缓存。
4. 优化提交必须包含同条件下的前后数据，不能只提交 Lighthouse 单次分数。
5. 不允许通过移除动画、降级 Markdown、隐藏首屏内容或改变布局来换取指标。
6. `npm run lint`、`npm run typecheck`、`npm test` 全部通过。
7. 生产构建和 Worker dry-run 通过，不新增构建警告；无法移除的旧警告需在交付说明中列出。

## 5. 实施阶段

### 阶段 A：建立基线，不改业务代码

使用 Chrome DevTools Performance/Network 完成以下采样：

1. 对第 3 节各网页场景保存 trace、网络瀑布图和关键截图。
2. 记录 HTML、CSS、JS、字体、图片、API 的传输体积与加载顺序。
3. 区分服务器等待、网络传输、脚本执行、样式计算、布局和绘制成本。
4. 标出长任务、布局偏移来源、重复请求和未使用的首屏资源。
5. 对线上 Worker 请求记录 `cf-cache-status`、`server-timing`（若有）、缓存头和 TTFB。
6. 将结果填入第 8 节表格，再决定阶段 B～E 的具体顺序。

阶段 A 的退出条件：至少找到一个由 trace 或请求数据支持的主要瓶颈，且能够说明它属于浏览器、Worker、D1、资源或缓存中的哪一层。

### 阶段 B：路由与富文本资源隔离

重点审查文件：

- `site/features/markdown/MarkdownRenderer.tsx`
- `site/features/markdown/MarkdownMermaid.tsx`
- `site/features/admin/VditorEditor.tsx`
- `site/vite.config.ts`

候选动作必须逐项验证：

1. 确认 Mermaid 是否只在检测到 `mermaid` 代码块后加载。
2. 确认首页、归档、普通文章和登录页不会预加载 Vditor 及其 Graphviz/MathJax/Highlight 资源。
3. 检查 Vditor 构建产物的重复目录是否源于静态复制配置；只有确认不影响运行后才能去重。
4. 检查代码高亮是否把不需要的语言全集带入公开页面；若是，优先采用框架/库支持的按需语言集合。
5. 路由拆分后验证主题切换、Markdown 全语法、流程图和编辑器即时预览。

优先采用现有动态导入和路由边界，避免新造加载器。

### 阶段 C：Worker、D1 与缓存

重点审查文件：

- `site/db/bootstrap.ts`
- `site/db/queries.ts`
- `site/app/api/archive/route.ts`
- `site/app/api/reader/[slug]/route.ts`
- `site/app/api/settings/route.ts`
- `site/app/api/posts/route.ts`

实施步骤：

1. 测量 `ensureDatabase()`、设置查询、分类查询、列表查询和文章查询各自耗时。
2. 确认 `ensureDatabase()` 是否在每次请求执行实际 DDL/种子检查；若只是已解析 Promise，则不要无意义重写。
3. 检查列表查询是否读取了正文大字段。归档、搜索和卡片只取真实需要的列。
4. 检查同一请求中能否安全并行的独立查询，避免无依据串行等待。
5. 仅对完全公开、与身份无关的 GET 响应评估 `s-maxage` 与 `stale-while-revalidate`。
6. 设计缓存失效方式后再加缓存：文章发布、撤回、分类或站点设置变化后必须在可接受时间内生效。
7. 后台、草稿、空间私密内容、预览令牌、OAuth/MCP 与登录接口继续 `private/no-store`。

任何 Schema 或索引修改都需要提供迁移、重复执行、中断恢复和回滚说明；没有查询计划证据时不新增索引。

### 阶段 D：CSS、字体、图片与渲染稳定性

1. 使用 Coverage 确认首屏未使用 CSS 的真实比例，避免直接拆全局样式造成视觉回归。
2. 检查字体文件、字重、`font-display` 和回退字体，减少文字闪烁和布局偏移。
3. 为首屏图片提供明确尺寸，优先复用现有图片管线，避免 CLS。
4. 对非首屏图片使用合理的懒加载；首屏 LCP 图片不得错误懒加载。
5. 保持暗色/明亮主题一致，特别回归代码块、Mermaid、表格、弹窗和导航岛。

### 阶段 E：持续预算与回归

1. 在现有测试体系中补充最少但完整的性能回归检查，不为每个指标新建脚本。
2. 构建阶段至少报告主要客户端入口和超过阈值的 chunk；阈值应基于阶段 A 的基线设定。
3. 若引入自动 Lighthouse/trace，固定运行环境并保存趋势，避免用不稳定的单次 CI 分数阻断发布。
4. 每次只合入一类优化，便于回滚和归因。

### 12.1 本地缓存一致性改造（2026-09-10）

- 新增 D1 `public_cache_state` 单行版本号。公开文章发布、撤回、移入/移出空间或内容变化，以及分类、站点设置、公开内容页变化时，由数据库触发器递增版本；单纯浏览量变化和私密草稿编辑不会递增。
- 公开 HTML 的 Cache API 键包含该版本号，因此不同 Cloudflare 机房都会在下一次请求读取到新版本并绕开旧缓存，不依赖只对单机房生效的 `caches.default.delete()`。
- 缓存版本读取失败时直接绕过缓存，不用猜测版本继续返回可能过期的页面；后台、API、RSC、OAuth、MCP 和私密预览仍不进入公开文档缓存。
- 复核失败路径后进一步收紧：修订号缺失或 D1 查询异常时，公开 HTML 不仅绕过 Cache API，还会显式返回 `Cache-Control: no-store`，避免下游共享缓存误存无法安全失效的响应；该分支已有直接单元测试。
- 有可靠主动失效后，公开 HTML 边缘 TTL 从 `120s` 延长到 `3600s`，降低周期性冷回源概率；浏览器仍为 `max-age=0`。
- 本地真实请求验证：迁移前首次请求绕过缓存；初始化后依次为 `MISS → HIT`。手动将版本从 `1` 递增到 `2` 后，下一次请求立即变为 `MISS`，随后重新 `HIT`。本次本地版本读取约 `23–63ms`，缓存命中总处理约 `25–38ms`，回源约 `257–298ms`。
- 精确触发器测试验证：公开内容变化会失效；浏览量变化、私密草稿创建和私密文章内容编辑不会造成缓存抖动。

以上是部署前的待验收项；实际部署后的 D1 版本读取、HIT/MISS 和私密边界结果记录在 12.2。由于本轮没有发布或修改公开正文，跨地域“发布后失效”仍由触发器自动测试和本地真实失效闭环提供证据，不用生产内容写入制造额外风险。
