# XINGYU MCP 多客户端 OAuth 2.1 接入设计稿

**版本：** v1.0
**目标域名：** `zhangwansen.click`
**MCP Endpoint：** `https://zhangwansen.click/mcp`
**状态：** 待开发
**适用客户端：** ChatGPT、Grok、未来其他标准 MCP Client

---

## 1. 项目目标

XINGYU 当前已经存在一条可工作的 MCP 写作通道：

```text
ChatGPT
   │
   │ Authorization: Bearer XINGYU_BLOG_MCP_TOKEN
   ▼
https://zhangwansen.click/mcp
   ▼
XINGYU
```

本次改造**不替换、不删除现有鉴权**。

在现有系统旁边增加标准 OAuth 2.1 Authorization Server，使 Grok 可以通过 OAuth + PKCE 接入：

```text
                         ┌─────────────────────┐
                         │   ChatGPT（现有）    │
                         │ Static Bearer Token │
                         └──────────┬──────────┘
                                    │
                                    ▼
                         ┌─────────────────────┐
                         │                     │
                         │      /mcp           │
                         │                     │
                         └──────────▲──────────┘
                                    │
                                    │ OAuth Access Token
                                    │
                         ┌──────────┴──────────┐
                         │       Grok          │
                         └──────────▲──────────┘
                                    │
                              OAuth 2.1 + PKCE
                                    │
                   ┌────────────────┴────────────────┐
                   │                                 │
         /oauth/authorize                   /oauth/token
                   │                                 │
                   └──────────────┬──────────────────┘
                                  ▼
                         XINGYU OAuth Server
```

最终效果：

```text
旧 ChatGPT       ✅ 不改配置继续使用
Grok             ✅ OAuth 接入
未来 ChatGPT     ✅ 可选迁移到 OAuth
其他 MCP Client ✅ 可继续扩展
```

MCP 当前 HTTP 授权规范要求 OAuth 授权服务遵循 OAuth 2.1，MCP Server 提供 Protected Resource Metadata，并通过 Authorization Server Metadata 暴露授权能力；授权请求还需要面向具体 MCP Resource，访问 MCP 时使用 Bearer Access Token。

# 2. 设计原则

### 2.1 向后兼容

现有：

```text
XINGYU_BLOG_MCP_TOKEN
```

继续有效。

OAuth 上线当天，不要求修改 ChatGPT。

### 2.2 双鉴权

`/mcp` 同时接受：

```text
Legacy Token
+
OAuth Access Token
```

### 2.3 Public OAuth Client

Grok 使用：

```text
Authorization Code
+
PKCE S256
+
无 Client Secret
```

Client Secret 不等于现有 `XINGYU_BLOG_MCP_TOKEN`，两者完全独立。

MCP OAuth 对授权码流程要求 PKCE，并要求客户端确认服务端支持 PKCE；当前规范要求能够使用时采用 `S256`。

### 2.4 最小权限

OAuth 权限分为：

```text
xingyu.read
xingyu.draft
xingyu.publish
offline_access
```

默认不给 AI 客户端公开发布权限。

### 2.5 OAuth 授权 ≠ 发布确认

即使 Grok 获得：

```text
xingyu.publish
```

XINGYU 当前已有的：

```text
publish_post 必须明确确认
unpublish_post 必须明确确认
update_page 必须确认
修改已发布文章必须确认
```

仍然保留。

OAuth Scope 是“能不能做”。

XINGYU 的确认机制是“这一次是否允许做”。

两层不能合并。

# 4. Protected Resource Metadata

Endpoint：

```text
GET /.well-known/oauth-protected-resource/mcp
```

返回：

```json
{
  "resource": "https://zhangwansen.click/mcp",
  "authorization_servers": [
    "https://zhangwansen.click"
  ],
  "scopes_supported": [
    "xingyu.read",
    "xingyu.draft",
    "xingyu.publish",
    "offline_access"
  ]
}
```

其中最重要的是：

```text
resource
=
https://zhangwansen.click/mcp
```

所有给 XINGYU MCP 使用的 OAuth Token 都必须绑定到这个 Resource。

不得接受给其他 API 签发的 Access Token。

# 7. Grok Redirect URI

这是整个配置中**唯一不能由 XINGYU 自己猜出来的核心参数**。

来源：

```text
Grok
```

第一次调试时：

```text
Grok
  ↓
GET /oauth/authorize
```

XINGYU 暂时记录：

```text
client_id
redirect_uri
scope
state
resource
code_challenge
code_challenge_method
```

然后从日志中取得真实：

```text
redirect_uri
```

确认它确实属于 Grok/xAI 后，再保存进：

```text
oauth_clients.redirect_uris
```

必须：

```text
完全匹配
```

例如数据库实际保存某个：

```text
https://<Grok实际提供的地址>/callback
```

以后收到：

```text
https://<其他地址>/callback
```

直接拒绝。

不允许：

```text
*
https://grok.com/*
*.grok.com
```

OAuth/MCP 授权规范要求严格验证 redirect URI，以避免开放重定向攻击。

# 8. OAuth Scope 设计

## 8.1 `xingyu.read`

允许：

```text
list_categories
search_posts
get_post
get_page
list_mcp_activity
```

不可修改任何博客数据。

---

## 8.2 `xingyu.draft`

包含：

```text
create_draft
```

以及：

```text
update_post
```

但只有当目标文章：

```text
status = draft
```

时允许。

---

## 8.3 `xingyu.publish`

这是高权限 Scope。

允许：

```text
publish_post
unpublish_post
update_page
```

以及：

```text
update_post
```

当目标：

```text
status = published
```

时必须拥有该 Scope。

因此 `update_post` 的权限不是固定的：

```text
update_post
   │
   ├─ 当前文章 = draft
   │      ↓
   │  xingyu.draft
   │
   └─ 当前文章 = published
          ↓
      xingyu.publish
```

这样可以避免 Grok 只拿到“草稿写入权限”，却通过 `update_post` 修改线上文章。

# 10. `/mcp` 双鉴权设计

所有 MCP Request：

```text
Authorization: Bearer <TOKEN>
```

进入统一 Auth Gateway。

逻辑：

```text
                 Bearer Token
                      │
                      ▼
             ┌─────────────────┐
             │ Token 有效吗？   │
             └────────┬────────┘
                      │
          ┌───────────┴───────────┐
          ▼                       ▼

 XINGYU_BLOG_MCP_TOKEN       xy_at_xxxxxxx
          │                       │
          ▼                       ▼
    Legacy Auth              OAuth Token DB
          │                       │
          ▼                       ▼
    FULL LEGACY              检查过期时间
    PERMISSION               检查 resource
                             检查 client
                             检查 scopes
          │                       │
          └───────────┬───────────┘
                      ▼
                  MCP Router
```

伪代码：

```ts
async function authenticateMcp(req) {
  const bearer = getBearerToken(req)

  if (!bearer) {
    throw oauthUnauthorized()
  }

  // 兼容当前 ChatGPT
  if (safeEqual(bearer, process.env.XINGYU_BLOG_MCP_TOKEN)) {
    return {
      authType: "legacy",
      clientId: "legacy-chatgpt",
      scopes: [
        "xingyu.read",
        "xingyu.draft",
        "xingyu.publish"
      ]
    }
  }

  // OAuth Access Token
  if (bearer.startsWith("xy_at_")) {
    return authenticateOAuthAccessToken(bearer)
  }

  throw oauthUnauthorized()
}
```

Legacy Token 比较必须使用恒定时间比较，避免普通字符串比较带来的时序泄漏。

同时禁止把完整 Token 写进日志。

# 11. 未授权 `/mcp` Response

没有 Authorization：

```http
HTTP/1.1 401 Unauthorized
WWW-Authenticate: Bearer resource_metadata="https://zhangwansen.click/.well-known/oauth-protected-resource/mcp", scope="xingyu.read"
```

Body 可以保持简洁：

```json
{
  "error": "unauthorized"
}
```

MCP 当前规范要求无效或过期 Access Token 返回 `401`；Scope 不足使用 `403`，Protected Resource 可以通过 `WWW-Authenticate` 指向 Resource Metadata。

# 12. `/oauth/authorize` 授权流程

Grok 发起：

```text
GET /oauth/authorize

response_type=code
client_id=grok-xingyu
redirect_uri=<grok callback>
scope=xingyu.read xingyu.draft offline_access
state=<random>
resource=https://zhangwansen.click/mcp
code_challenge=<PKCE challenge>
code_challenge_method=S256
```

服务端依次校验：

```text
response_type == code

client_id 是否存在

client 是否 enabled

redirect_uri 是否完全匹配

resource ==
https://zhangwansen.click/mcp

scope 是否属于 allowed_scopes

code_challenge 是否存在

code_challenge_method == S256
```

任一失败：

```text
不签发 Authorization Code
```

# 15. Authorization Code

点击：

```text
允许访问
```

生成随机 Authorization Code：

```text
xy_code_<random>
```

设计参数：

```text
随机强度：
至少 32 bytes

有效期：
5 分钟

使用次数：
1 次

数据库：
只保存 SHA-256 Hash

明文：
只返回给 Client
```

数据库绝不保存：

```text
xy_code_完整原文
```

而保存：

```text
SHA256(xy_code_...)
```

成功后：

```http
302 Location: <registered_redirect_uri>?code=<authorization_code>&state=<original_state>
```

`state` 原样返回给 Grok。

# 16. `/oauth/token` Authorization Code Exchange

Grok：

```http
POST /oauth/token
Content-Type: application/x-www-form-urlencoded
```

Body：

```text
grant_type=authorization_code
code=...
client_id=grok-xingyu
redirect_uri=...
code_verifier=...
resource=https://zhangwansen.click/mcp
```

XINGYU 校验：

```text
code 是否存在
code 是否过期
code 是否已使用

client_id 是否一致

redirect_uri 是否与授权请求完全一致

resource 是否一致

PKCE:
BASE64URL(SHA256(code_verifier))
==
code_challenge
```

所有条件通过后：

```text
在同一事务中：

1. Authorization Code 标记 consumed
2. 生成 Access Token
3. 如有 offline_access，生成 Refresh Token
```

# 17. Access Token 设计

使用 opaque token，不使用 JWT。

格式：

```text
xy_at_<random>
```

例如逻辑结构：

```text
prefix    = xy_at_
random    = 32~48 bytes cryptographic random
encoding  = base64url
```

数据库只保存：

```text
SHA256(access_token)
```

推荐：

```text
Access Token TTL:
60 分钟
```

这是 XINGYU 自己的产品选择，不属于协议固定值。

Access Token Record：

```text
client_id
subject
scope
resource
expires_at
revoked_at
created_at
last_used_at
```

# 18. Refresh Token

只有请求包含：

```text
offline_access
```

才签发：

```text
xy_rt_<random>
```

Token Response：

```json
{
  "access_token": "xy_at_xxxxxxxxx",
  "token_type": "Bearer",
  "expires_in": 3600,
  "refresh_token": "xy_rt_xxxxxxxxx",
  "scope": "xingyu.read xingyu.draft offline_access"
}
```

ChatGPT 官方目前特别建议 OAuth MCP 配置 Refresh Token / `offline_access`，否则原始授权过期后可能失去连接、需要用户重新认证。

所以 XINGYU 第一版就把 Refresh Token 做好，避免以后再改协议。

---

# 19. Refresh Token Rotation

请求：

```text
grant_type=refresh_token
refresh_token=xy_rt_xxxxx
client_id=grok-xingyu
```

成功：

```text
旧 Refresh Token
       ↓
立即失效
       ↓
生成新 Access Token
+
生成新 Refresh Token
```

形成：

```text
RT1 → RT2 → RT3 → RT4
```

如果已经用过的：

```text
RT1
```

再次出现：

```text
Refresh Token Reuse Detected
```

则：

```text
撤销该 Token Family
```

要求客户端重新授权。

当前 MCP OAuth 安全规范要求 public client 的 Refresh Token 采取 rotation 等保护措施。

# 23. Tool Annotations

XINGYU MCP Tool 建议补充标准 Tool Annotations。

MCP Schema 支持：

```text
readOnlyHint
destructiveHint
idempotentHint
openWorldHint
```

这些是给客户端理解工具风险的提示，不能代替真正的服务器权限检查。

建议：

| Tool                | readOnly | destructive | idempotent |
| ------------------- | -------: | ----------: | ---------: |
| `list_categories`   |     true |       false |       true |
| `search_posts`      |     true |       false |       true |
| `get_post`          |     true |       false |       true |
| `get_page`          |     true |       false |       true |
| `list_mcp_activity` |     true |       false |       true |
| `create_draft`      |    false |       false |      false |
| `update_post`       |    false |        true |       true |
| `update_page`       |    false |        true |       true |
| `publish_post`      |    false |        true |       true |
| `unpublish_post`    |    false |        true |       true |

这些 Annotation 只是描述。

真正的权限仍必须：

```text
Tool Handler
↓
requireScope(...)
```

# 24. Tool Handler 权限模式

例如：

```ts
async function createDraft(ctx, args) {
  requireScope(ctx.auth, "xingyu.draft")

  return createDraftInternal(args)
}
```

`publish_post`：

```ts
async function publishPost(ctx, args) {
  requireScope(ctx.auth, "xingyu.publish")

  requireExplicitUserConfirmation(ctx)

  return publishPostInternal(args)
}
```

`update_post`：

```ts
async function updatePost(ctx, args) {
  const post = await getPost(args.identifier)

  if (post.status === "published") {
    requireScope(ctx.auth, "xingyu.publish")
    requireExplicitUserConfirmation(ctx)
  } else {
    requireScope(ctx.auth, "xingyu.draft")
  }

  return updatePostInternal(args)
}
```

这一步非常关键。

**绝不能仅在 OAuth 登录时判断 Scope，然后内部 Tool 不再判断。**

# 25. Scope 不足

例如 Grok Token：

```text
xingyu.read
xingyu.draft
```

调用：

```text
publish_post
```

返回：

```http
HTTP/1.1 403 Forbidden
```

例如：

```json
{
  "error": "insufficient_scope",
  "required_scope": "xingyu.publish"
}
```

不要返回：

```text
401
```

因为它已经登录，只是没有权限。

# 26. Token Resource Binding

所有 OAuth Token 都保存：

```text
resource =
https://zhangwansen.click/mcp
```

验证时：

```text
token.resource
==
expectedMcpResource
```

否则拒绝。

例如一个未来用于：

```text
https://zhangwansen.click/api/admin
```

的 Token：

```text
不能拿去调用 /mcp
```

MCP 当前授权规范明确要求客户端在授权和 Token 请求中指定目标 Resource，Resource Server 也需要确认 Token 是为自己签发的，禁止 Token Passthrough。

# 29. 安全要求

必须做到：

```text
所有 Endpoint HTTPS

redirect_uri 完全匹配

PKCE 只接受 S256

Authorization Code 一次性

Access Token 短生命周期

Refresh Token rotation

Token 数据库只保存 hash

resource 严格校验

Scope 每次 Tool Call 强制校验

禁止 Token 出现在 URL Query

禁止 Token 写日志

登录后的 Consent POST 做 CSRF 防护

/oauth/token 做 Rate Limit

/oauth/authorize 做 Rate Limit

Authorization Code Exchange 原子事务

Refresh Token Rotation 原子事务
```

MCP OAuth 规范要求 HTTP 授权端点通过安全通信，并规定 Bearer Access Token 应通过 `Authorization` Header 携带，而不是放进 URL Query。

# 30. 不使用 JWT

第一版建议：

```text
不要 JWT
```

采用：

```text
Opaque Access Token
+
数据库查询
```

原因：

```text
XINGYU 是单用户个人服务

OAuth Client 数量极少

需要方便立即撤销

无需 JWKS

无需 key rotation 基础设施

无需处理 JWT audience / kid / signing key 运维
```

例如：

```text
xy_at_YHFx.....
```

服务器：

```text
SHA256(token)
↓
oauth_access_tokens
```

即可。

未来如果 XINGYU 做成多人 SaaS，再考虑 JWT。
